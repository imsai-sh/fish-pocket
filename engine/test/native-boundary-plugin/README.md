# dsh-plugin-native-boundary-check

**边界验证插件，不是接入范例。** 它的作用是从外面验证一件事，不是给你照抄。

它住在 `engine/test/` 而不是 `examples/`，这是刻意的：插件调本机 API **不在当前设计目标里**（[§1.1](../../../docs/native-services.md)），而一个叫 `examples` 的目录本身就是在招手。

装上它就验证了设计里那个核心主张（[`docs/native-services.md`](../../docs/native-services.md) §5.3）：

> 系统授权给了之后，引擎本体和第三方插件是同一类调用方，应用层不再设授权门。

这个插件没有第二次授权，也没有任何特权通道。它向容器要 `iosNative`，拿到的
和智能体自己的工具拿到的**完全一样**——不多也不少。

## ⚠️ 不要照着它写插件

本机能力是**做给智能体用的**，插件调它不在目标里（§1.1）。而且它**不是公开
API**（§5.6）：能力名、操作名、参数形状都随版本改，不作任何兼容承诺：

- **智能体不受影响**——它每次对话都重读 `SKILL.md`，能力改名改一行文档就行。
- **硬编码的插件会直接断**，而且是悄无声息地断在别人手机上。

这张能力表光是这一周就重排过三次（砍掉 NLP 两个废操作、`eta` 改成只收坐标、
`classify` 去掉置信度阈值）。在有兼容承诺的世界里，每一次都是破坏性变更。

这个文件本身也是按「可能随时对不上」写的：每次调用都包着，报告说的是它**发现
了什么**，而不是假定某个形状成立。

够得到和被承诺是两件事。够得到是事实（拦不住，§5.3.1 有实测数据）；不承诺是
我们的选择。

## 两个工具

| 工具 | 回答的问题 |
|---|---|
| `native_check` | 边界还在吗？列出本机能力，并验证没实现的操作确实被拒 |
| `daily_briefing` | 这东西有用吗？读手机状态 + 今天的日程，可以念出来 |

`native_check` 是 §9.3 那条教训的产品化：它去调两个**不存在**的东西——
`calendar.wipe`（能力在、操作不在）和 `healthkit.read`（能力根本不在）——
然后报告有没有被拦住。两条都该被拒；任何一条通过了都是 bug。

## 装上它

插件安装支持 npm 包名、Git 地址、tarball 和**绝对本地路径**。这个包在仓库的
子目录里，没发到 npm，所以走本地路径最省事：

1. 让智能体把仓库拉到它自己的工作区（引擎自带 git）：

   > 把 https://github.com/imsai-sh/fish-pocket 克隆到当前目录

2. 让它告诉你插件目录的绝对路径：

   > `examples/dsh-plugin-native-boundary-check` 的绝对路径是什么

3. 设置 → 插件 → 安装，把那个路径粘进去。

装完要重启引擎（安装操作本来就会提示）。

> **为什么不能自己拷文件进去：** App 的文档目录没有对「文件」App 开放，所以
> 手机上没有别的途径把文件放到引擎能读到的地方。让智能体去 clone 是目前唯一
> 不需要先发包的装法。

## 跑一遍该看到什么

装好之后跟智能体说：

> 我今天怎么样

第一次会弹系统的日历授权弹窗（如果还没授权过）。然后：

> 检查一下本机能力

`native_check` 应该报告两条都被拒：

```
calendar.wipe   → refused (capability 'calendar' has no operation 'wipe')
healthkit.read  → refused (unknown capability 'healthkit')
```

最后去**设置 → 本机能力 → 使用记录**。你会看到刚才那次日历读取，
**调用方写的是 `dsh-plugin-native-boundary-check`，不是「智能体」**。

这正是整套设计要你看见的东西：插件和本体走同一条路、拿同样的权限，
区别只在事后那一行记录里——而那一行也只是插件自报的名字，不是证据。
