# 本机服务接入设计（日历 / 提醒 / 健康 / 运动 …）

本文是**设计方案，尚未实现**。目标是让引擎和插件能用上 iPhone 自己的数据——日程、提醒、健康、运动、位置——这样智能体才可能成为个人助理，而不只是一个装在手机上的编码工具。

范围：能力清单、授权模型、实现路线、安全边界的真实强度、合规风险、分期落地。界面细节按 `docs/design/README.md` 的规矩另出稿。

---

## 1. 为什么这件事值得做，以及它改变了什么

现在的工具集都是"对文件和命令动手"。接入本机服务后智能体才拿到**关于你的事实**：今天有什么会、昨晚睡了多久、下周三是否有空。这是"编码 Agent"到"个人助理"的分界。

但它同时把这个 App 从「只碰自己沙盒」变成「碰用户最私密的数据」，而且：

- 智能体读到的内容**会发给模型服务商**（默认 DeepSeek）。日程标题、参会人、健康指标都算。
- 第三方插件**在本机以用户的权限运行，并且可以联网**（`PRIVACY.md` 已经这么写了）。
- 写操作有真实后果：删掉一个日历事件、改掉一个提醒，没有撤销。

所以这件事的难点不在调 API，在于**授权模型要立得住**，以及 `PRIVACY.md`、`PrivacyInfo.xcprivacy`、系统弹窗上的用途描述三者要跟上。

### 1.1 服务对象：智能体，不是第三方插件

**这些能力是做给智能体用的。** 第三方插件调本机 API 不在当前目标里——安全模型没想清楚，也还看不到足够的价值场景。将来真要做，那是另一件事（要配一套版本化的 API 协议，见 §5.6）。

这句话容易和另一句搞混，必须分开记：

| | |
|---|---|
| **目标** | 面向智能体。不为插件设计，不为插件保证，不写给插件开发者看 |
| **事实** | 插件够得到，而且**拦不住**（§5.3.1 有实测数据） |

把目标说成「插件不能用」就是撒谎，而本文后面所有的护栏都建立在承认这个事实之上：**正因为拦不住，安装页的警告（§4.1.1）和使用记录（§5.4）才是真正承重的那两样。**

这一条是 2026-11-10 对最初设计的修正。原来的设定是「把本机能力同时暴露给 DSH 本体和第三方插件」，§2 那整节的分析（按调用方授权守不住）仍然成立，但它现在的用途变了：它不再是「所以干脆都开放」的理由，而是「所以别承诺、别引导、把警告和审计做扎实」的理由。

同类产品 OpenMinis 已经把这条路走通了，它的设计、分类标准和踩过的坑都值得对照——见 §9。

## 2. 先回答一个前置问题：DSH 支不支持第三方插件的权限控制？

**不支持。现在没有，也不可能靠引擎自己长出来。** 查证结论（引擎 `@deepseek-ai/dsh@0.2.1-rc.4`）：

| 维度 | 现状 |
|---|---|
| 插件形态 | npm 包（bundle），通过 `pluginManager.installBundle` 用 pnpm 装进 profile，向 cordis 注册一行插件 |
| 运行隔离 | **没有**。插件是纯 JS，和引擎跑在同一个 Worker、同一个 isolate 里，可以 `require('node:fs')`、`fetch`、读 `~/.credentials.yaml`、`process._linkedBinding('dsh_git')` |
| 能力声明 | **没有**。package.json 里没有 permissions / capabilities 字段，装之前无法知道它要什么 |
| 现成的权限概念 | 有两个，但都不是"插件权限"：<br>① `permissionPresets`（`read-only` / `workspace-write` / `full-access`）是**会话**的沙盒模式 + 审批策略，管的是文件和命令；<br>② `ctx.approval.request()` 是**一次性工具审批**，粒度是「某个 agent 的某次工具调用」，只有「允许一次 / 拒绝」，没有「总是允许」 |
| 插件身份可否识别 | 诚实的能，不诚实的不能。见 §2.1、§2.2 实测 |

也就是说：**既没有隔离，也没有可信的身份**。这决定了整个设计的性质——

> 能建的是一层**授权网关**：让用户知道这个 App 能碰哪些本机数据、随时能关、事后能查。它**不是**防恶意插件的沙箱，也**不能**区分"本体在用"还是"某个插件在用"。

这不是推卸。真正的护栏只有两处，都不在 JS 里：**iOS 的系统权限**，和**原生侧对写操作的当次确认**（§5.3）。

### 2.1 调用方归因：实测结论

cordis 的 service tracker 把服务方法里的 `this.ctx` 换成**调用方**的 context（`tracker.property === 'ctx'`，见 cordis `createTraceable`），所以服务内部能知道是谁在调它。拿 `@deepseek-ai/cordis` 实跑验证过，结果如下：

| 调用方 | `fiber.name` | `fiber.runtime.name` | fiber 链 |
|---|---|---|---|
| 引擎本体（根 context） | `root` | *undefined* | `[root, (anon)]` |
| 第三方插件直接调 | `dsh-plugin-foo` | `dsh-plugin-foo` | `[dsh-plugin-foo, (anon)]` |
| 插件加载的子插件调 | `foo-internal-child` | `foo-internal-child` | `[foo-internal-child, dsh-plugin-bar, ✗]` |

插件 `apply` 执行期间和之后（定时器回调里）结果一致，归因本身是稳定的。三个坑：

1. **根 fiber 没有 `runtime.name`**，只有 `fiber.name === 'root'`。想识别本体就得用 `fiber.name`。
2. **只取直接 fiber 名不够**。插件内部再 `ctx.plugin(...)` 时，拿到的是内部子插件名，不是那个 npm 包。
3. **`fiber.parent` 遍历会抛**。cordis 对未声明 inject 的属性访问报 `cannot get property "parent" without inject`，链走到某一层就断。必须 try/catch，且不能假设能走到根。

### 2.2 为什么不能按「谁」授权：一行就穿了

归因能分辨诚实的调用方，但**挡不住不诚实的**。同样实跑验证，拿三种手段去冒充引擎本体：

| 插件的写法 | `fiber.name` | 是否 === 本体的 fiber 对象 | 结果 |
|---|---|---|---|
| `ctx.iosNative.read()`（老实调用） | `dsh-plugin-evil` | no | 识别为插件 |
| `ctx.iosNative[Symbol.for('cordis.original')].read()` | `IosNative` | no | 识别为服务自己，非本体 |
| **`ctx.root.iosNative.read()`** | **`root`** | **YES** | **与本体真实调用完全同一** |

第三行是致命的：`ctx.root` 是 cordis 带文档注释的公开 API（"The root context of the application"），插件把 `ctx.` 换成 `ctx.root.` 就拿到了和引擎本体**同一个 fiber 对象**。不是"归因看起来像"，是真的分辨不出来——没有任何字段能区分。

**所以调用方身份不能当授权依据。** 一个"本体免授权、插件要授权"的设计，拦得住的只有不打算绕的插件；它给用户的是虚假的安全感，还要为此维护两条路径。

结论：**把本体和插件看成同一类调用方**。身份降级为**审计标签**（标明自报、不可信），授权主体改成「能力」本身——见 §4。

## 3. 能接什么，代价是什么

iOS 这些都是系统框架，和「控制其他 App」（做不到）不是一回事，技术上都可行。按「助理价值 ÷ 代价」排：

| 能力 | 框架 | Info.plist / 能力 | 代价与坑 | 建议 |
|---|---|---|---|---|
| **日历读写** | EventKit | `NSCalendarsFullAccessUsageDescription` | **读必须 full access**，而 full access 同时给了写（见 §4.0）。授权前 fetch 过的话，授权后要 `EKEventStore.reset()` | **第一期** |
| **提醒读写** | EventKit | `NSRemindersFullAccessUsageDescription` | 同上。和 DSH 自己的 todo / `dsh-schedule` 职责要划清（见 §4.4） | **第一期** |
| **本地通知** | UserNotifications | 无用途描述，只需运行期请求 | 最便宜的"提醒我"实现，不碰提醒 App | **第一期** |
| **运动 / 步数** | CoreMotion | `NSMotionUsageDescription` | `CMPedometer` 只给最近 7 天，再往前要 HealthKit | 第二期 |
| **健康读** | HealthKit | HealthKit capability（entitlement）+ `NSHealthShareUsageDescription` | **合规最重，见 §6.1**。读权限状态查不到（Apple 故意不给，防推断），只能"读到空"当没授权。逐类型授权 | 第二期，**要先决定做不做** |
| **位置** | CoreLocation | `NSLocationWhenInUseUsageDescription` | 粗/精粒度两档。后台定位别碰 | 第二期 |
| **通讯录读** | Contacts | `NSContactsUsageDescription` | 隐私敏感度高于日历（牵涉第三人），而且会被发给模型 | **已做，只读**（§3.2） |
| **照片库** | PhotoKit | `NSPhotoLibraryUsageDescription` | 读必须 read-write，没有只读档，所以开了就同时给了写。删照片、删相簿、隐藏照片时 iOS 每次都会自己弹确认框。iOS 16 起隐藏的照片对 App 完全不可见（隐藏相簿计数为 0），所以只能隐藏、不能取消隐藏 | **已做，读写**：读元数据、导出给 `vision`；整理相册（建/改名/删相簿、放进/移出相簿、收藏、隐藏、存入、删除）按写入策略走。iOS 自己弹框的那几项只在「只读」时被 App 拦下，其余交给 iOS 的框，不叠第二层。不做像素编辑 |
| **健康写** | HealthKit | `NSHealthUpdateUsageDescription`（已填，只声明不写） | 写健康数据责任太大，且"不得写入虚假数据"是硬条款 | **不做** |
| **屏幕使用时间** | DeviceActivity | 需特批 entitlement | 家长控制专用，申请门槛高 | 不做 |

### 3.1 别漏了不需要隐私权限的那一批

上表全是要用户授权的。但对"个人助理"来说，有一批能力**不碰个人数据、不需要任何权限弹窗**，价值却不低——OpenMinis 把它们单独归类且永不设门（§9.2）：

| 能力 | 框架 | 权限成本 |
|---|---|---|
| 本地通知 / 闹钟 | UserNotifications / AlarmKit | 通知要运行期请求一次；AlarmKit 在 iOS 26 起要 `NSAlarmKitUsageDescription` |
| 天气 | WeatherKit | 无用户权限。但 App ID 要开通 WeatherKit（能力和 App Service 两处），包里要有 `com.apple.developer.weatherkit`。**代码已接好，开通还没做**（§3.2） |
| 地图 / 打开 URL | MapKit / `UIApplication.open` | 无 |
| 朗读 / 语音合成 | AVSpeechSynthesizer | 无 |
| 设备信息（电量、型号、存储） | UIDevice 等 | 无 |
| 图像识别 / 自然语言 | Vision / NaturalLanguage | 无（纯本地计算） |

这批应该**优先做**：零授权成本、零合规风险、不需要本文的任何授权机制，而"提醒我 20 分钟后出门"、"今天要带伞吗"恰恰是助理最高频的请求。放进一期或单独一期都行。

另外两个和"助理"直接相关、但不属于本文的方向，先记一笔：

- **App Intents / 快捷指令**：把 dsh 暴露给 Siri 和快捷指令，是反方向（别人调我们）。价值很高，独立做。
- **HealthKit 后台投递**（`HKObserverQuery` + `enableBackgroundDelivery`）：数据变化时唤起智能体。等健康读稳定后再谈。


### 3.2 第三批：通讯录、撰写页、文件、音乐、天气

这五项是一起做的。它们的共同点是都直接对着「帮我办件事」：找到一个人、把话递出去、把文件拿进来或交出去、放首歌、看看要不要带伞。五项里只有通讯录和音乐带系统权限；另外三项没有权限也没有开关，原因各不相同，分别写在各自那一节里。

能力表里的五行（`native/ios-native/ios_native.m`）：

| 能力 | 操作 | 系统权限 | 写操作 |
|---|---|---|---|
| `contacts` | `search` `get` | 通讯录 | 无 |
| `compose` | `mail` `message` | 无 | 无（发送键是用户按的） |
| `files` | `pick` `export` | 无 | 无（保存位置是用户选的） |
| `music` | `search` `playlists` `now` `play` `pause` `next` `previous` | 媒体与 Apple Music | `play` `pause` `next` `previous` |
| `weather` | `current` `hourly` `daily` | 无 | 无 |

#### contacts：只读地查通讯录

**做什么。** 只读地查用户的通讯录，两个操作：

- `search`：按 `name`、`phone`、`email` 三者**之一**查，返回每个命中的 `id`、全名、公司、电话、邮箱。默认 25 条，上限 100 条，带 `total` 和 `truncated`。「给张三发短信」到这一步就够了，不需要第二次调用。
- `get`：拿 `id` 取整张名片，多出姓/名/中间名、昵称、职位、部门、邮寄地址（分字段 + `CNPostalAddressFormatter` 排好的一串）、生日、网址。

**故意不做的。**

- **不写。** iOS 的通讯录权限只有一档，读写一起给，所以「智能体不会动我的通讯录」不是系统保证的，是我们自己保证的。做法是 `caps_contacts.m` 里没有 `CNSaveRequest`，表里的 `writeOps` 是空的，没有东西需要把门。（照片以前也这样，后来因为有整理相册的需求，改成按写入策略开放写入。）
- **不猜查的是哪个字段。** 「138」可能是号码的一段也可能是公司名。原生侧去看查询长什么样再决定，就是替调用方回答了一个它没问的问题（§4.5）。所以由调用方说明字段，三个字段各自对应 Apple 写好的谓词，匹配规则是 Apple 的，上面不再叠东西。
- **不排序、不挑。** 命中按 store 给的顺序原样返回。两个「张三」哪个才对，只有用户知道；工具说明里要求智能体列出来问，而不是自己选一个，尤其是在给对方发东西之前。
- **不取备注和头像。** 备注（`CNContactNoteKey`）需要向 Apple 单独申请 entitlement，没有它时**整个 fetch 都会失败**，不只是少一个字段。头像对「要个电话号码」的调用方没用。
- **电话号码不规范化。** 用户怎么存的就怎么给。前面有没有 `+86` 正是调用方可能要看的。

**维护时要知道的坑。**

- **iOS 18 的「仅分享部分联系人」。** 这一档下 store 只从用户挑的那几位里作答，而且不说。「没查到」和「通讯录里没这个人」在这时是两回事，所以每个结果都带 `access`（`full` / `limited`），limited 时再带一句 `note`，渲染时放最前面；JS 侧空结果的那句话也跟着换成「分享的联系人里没有」。`CNAuthorizationStatusLimited` 只在 18 以上存在，部署目标是 17，所以放在 `@available` 里单独比较，不进 `switch`。授权页那一行同理显示「仅限你分享的那几位」，不写「已开启」。
- **授权结果读状态，不信回调的 `granted`。** `DshContactsGrantAccess` 在回调里重新读一次授权状态，full 和 limited 都报已授权。这样授权页和 handler 用的是同一个判断，不会各说各的。
- **`CNContactFormatter` 要的 key 必须在 `keysToFetch` 里。** 少了它不是返回空名字，是直接抛异常；而它要哪些 key 取决于用户的姓名顺序设置，所以用 `descriptorForRequiredKeysForStyle:`，不要手写。
- **没有年份的生日。** 大多数名片的生日不带年份，Contacts 用 `NSDateComponentUndefined`（即 `NSIntegerMax`）表示，不是 nil。不处理的话 JSON 里会出现一个十九位数的年份。现在是没有年份就不给 `year`，绝不补一个。
- **匹配有多宽是 Apple 的谓词定的，比直觉窄。** 实测（§7.5）：电话和邮箱都只认**整个**值，号码的一段、邮箱的一段都查不到；名字是按词的前缀匹配，公司名也算（`bell`、`Kate Bell`、`Creative` 能中，`ohn` 不中）。同一个号码前面多写一个国家码也可能查不到。工具说明和内置 skill 里把这几条都告诉了智能体：拿一段号码查出来的空结果，不等于没有这个人。
- **`id` 不是长期稳定的。** 它是统一联系人（unified contact）的标识，用户合并或拆开名片后会变。只适合 `search` 之后紧接着 `get`，不要让智能体存起来隔天再用。查不到时的报错会让它重新 `search`。`get` 用的是 `predicateForContactsWithIdentifiers:` 而不是 `unifiedContactWithIdentifier:`，这样「没有这个 id」是空数组，不用靠错误码去分辨。
- **审计摘要里只有名字。** 按名字查记「查询词 · 命中数」，查询词是调用方自己的话；按电话或邮箱查只记字段名和命中数，不记号码和地址本身。`get` 记这张名片的名字。审计列表是给用户看「谁碰过我的数据」的，不该变成通讯录的第二份拷贝。

#### compose：邮件和短信的撰写页

智能体把收件人、标题、正文、附件填好，弹出系统自带的撰写页（`MFMailComposeViewController` / `MFMessageComposeViewController`），**由用户自己点「发送」**。这个能力本身不发任何东西，也没有办法发：发送按钮是 Apple 的，画在另一个进程里，调用方点不到。道理和新建日程走系统事件编辑器是同一个（§4.3）。

两个操作：`mail`（`to` / `cc` / `bcc` / `subject` / `body` / `html` / `attachments`）和 `message`（`to` / `body` / `attachments`）。结果只有一个字段 `result`：`sent`、`cancelled`，邮件多一个 `saved`（存成了草稿）。系统报「失败」时走错误，不走结果。

**故意不做的事**

- **没有系统权限，也没有写入策略，不走 `DshNativeConfirmWrite`。** 用户点 Apple 的「发送」就是确认；在它前面再弹一个我们自己的确认框，只是把同一件事问两遍。因此表里 `writeOps` 是空的，设置里也没有它的三档开关。
- **不记使用记录。** 按现有规则，只有带系统权限的能力才写 `auditSummary`。代价是：经智能体发出去的邮件在「使用记录」里查不到，只在「邮件」的已发送里有。
- **邮件没有账户时不退回 `mailto:`。** `canSendMail` 为假就直接拒绝，并说明是「邮件」App 没有配置账户。`mailto:` 会离开 App，之后发没发我们不知道，结果就只能靠猜——猜错的后果是告诉用户「已发送」。它也带不了附件。调用方真想这么做，`open` 能力本来就能开 `mailto:`。
- **不替调用方改参数。** `to` 传成字符串不会被包成数组，文件夹不会被自动打包，`message` 里出现 `subject` 在 JS 层直接拒绝——悄悄丢掉的话，用户看到的草稿就和调用方以为的不一样。
- **附件大小不设上限。** 系统没有给现成的数字，自己定一个就是编的。「邮件」对过大的附件自己会提示。

**维护时要知道的坑**

- **「已发送」不等于送达。** `sent` 只表示交给了「邮件」的发件箱或「信息」。工具的描述和渲染结果都这么写，改文案时别写成「已送达」。
- **两个撰写页都是远端视图**，可以不走代理回调就消失（§4.3.2）。所以上屏走 `presentSystemController:failure:gone:`，`gone` 到来时代理还没答复，就回「撰写页在用户答复前关闭了，没有发出任何东西」，不回 `cancelled`——不是用户取消的。
- **撰写页不会自己关。** 代理里必须 `dismiss`，否则用户被一个按钮全都失效的页面挡住。
- **结果在页面收起之后才回**，不是在代理回调里立刻回。立刻回的话，「一次只开一个」的占位要等桥那边轮询到 `gone`（最多晚半秒多）才释放，同一轮里紧接着的第二封会被误拒成「已经开着一个」。收起回调没来时由 `gone` 兜底，回的仍是代理记下的结果。
- **附件路径必须在调用线程上解析**，不能挪到主线程：`dsh_root_real` 对相对路径用的是线程本地的当前目录，主线程没有。所有附件在弹出任何界面之前就检查完（存在、不是目录、可读），坏路径是一次调用方能改的拒绝，而不是一份少了附件的草稿。
- **代理是 weak 的**，会话对象靠文件里的静态变量活着；它同时就是「一次只开一个」的占位。释放时要比对是不是自己，因为 `gone` 可能在下一个会话已经占位之后才到。
- **模拟器里发不了。** `canSendMail` 和 `canSendText` 在模拟器上通常都是假，能验的只有参数检查、附件检查和两条拒绝；上屏、三种结果、附件是否带上，都只能在装了邮件账户、开了 iMessage 的真机上验。

#### files：从「文件」App 取文件、把文件交还给用户

**做什么。** 两个操作，都靠系统文件选择器（`UIDocumentPickerViewController`）完成：

- `pick`：弹出选择器，用户选中的文件被放进引擎文件系统的 `/home/dsh/.ios/files/<yyyyMMdd-HHmmss>/<原文件名>`，返回 `{files: [{path, name, bytes, type}], cancelled: false}`。`types` 可以写 UTI 或扩展名，不传就是任意文件；`multiple` 允许多选。用户关掉选择器返回 `{files: [], cancelled: true}`，这是正常结果，不是错误。
- `export`：把引擎里的文件或目录（`paths`）交给选择器，由用户选保存位置。返回 `{saved: true, count}`，取消时 `{saved: false}`。

**为什么没有系统权限、没有开关、也不走写入策略。** 选择器跑在系统进程里，App 在用户点选之前看不到任何文件，点选之后也只看到被选中的那几个。每次调用都必然停在系统界面上等用户操作，智能体按不了里面的按钮，所以选择器本身就是授权。再加一层开关或确认框，等于同一件事问两遍。`export` 也只会写到用户当场选的位置，因此不算 `writeOps`，也不带 `auditSummary`。

**故意不做的。**

- **不授予「活的文件夹」。** 这一版只有「拷进来」和「拷出去」。让引擎直接读写 iCloud 云盘里的某个目录，需要 security-scoped bookmark，还需要 `native/root` 支持把容器外的目录挂进引擎的文件系统视图，现在没有这个接口。后果是：改了选进来的文件，原件不会变，要再 `export` 一次才回到用户手里。
- **不改名、不去重。** 每次 `pick` 用一个按秒命名的新目录，文件保持原名。同一次多选里出现同名文件时，后一个会失败并报出来，不会覆盖前一个。
- **不猜类型。** `types` 里的字符串先当 UTI 查，再当扩展名查，只接受系统已声明的类型。系统不认识的扩展名（如 `jsonl`）会被拒绝，而不是生成动态类型。原因是 `image`、`spreadsheet` 这类误写也会得到一个动态类型，选择器打开后所有文件都是灰的，用户看不出为什么。被拒后调用方去掉 `types` 重试即可。
- **不清理。** `/home/dsh/.ios/files` 下的文件留到有人删为止，和 `photos` 的导出目录一样。

**维护时要知道的坑。**

- 两个操作都用 `asCopy:YES`，不能改。`pick` 不带它拿到的是容器外的原件，路径不在引擎视图里，访问权也只属于本进程；`export` 不带它是**移动**，用户一保存，引擎工作区里的原件就没了。
- 因为是 `asCopy:YES`，回调里的 URL 已经是 App 临时目录里的副本，所以不需要 `startAccessingSecurityScopedResource`，放进引擎目录用的是移动而不是再拷一份（大视频不必占两份空间）。
- 选择器是跨进程视图，可能不调用代理就消失。应答只结算一次：代理方法、桥的 `failure`、桥的 `gone` 三者之一。`answered` 在**进入代理方法时**就置位，因为 `gone` 触发时文件可能还在搬；`gone` 只在代理没应答时才报错，报的是「选择器在用户选择之前关闭了」，不说成用户取消（§4.3.2）。
- 同一时刻只允许一个选择器，第二次调用直接拒绝。占位在 `present` 之前设置，在 `gone` 里释放。
- 部分文件失败时，成功的照常返回，失败的列在 `failed: [{name, error}]` 里；全部失败才是错误。渲染时失败项排在最前面。
- 包文档（`.pages`、`.rtfd`）是目录，返回 `directory: true`，不给 `bytes`。`type` 是系统给的标识符，原样转发，可能是 `dyn.` 开头。
- `export` 在弹出选择器之前检查每个路径是否存在，否则用户选完位置才发现失败。`count` 是选择器回报的 URL 数量，不是请求的数量。

#### music：音乐资料库与系统播放器

`music` 让智能体在用户自己的音乐资料库里找歌、专辑、艺人、歌单，并控制「音乐」App 的播放。框架是 MediaPlayer，系统权限是「媒体与 Apple Music」（`NSAppleMusicUsageDescription`），权限名 `music`。

| 操作 | 读/写 | 做什么 |
|---|---|---|
| `search` | 读 | 按 `kind`（`song` 默认 / `album` / `artist` / `playlist`）在各自的名称字段里做包含匹配，按资料库自己的顺序返回，默认 25 条、最多 100 条，带 `total` 和 `truncated` |
| `playlists` | 读 | 列出全部歌单，最多 200 个 |
| `now` | 读 | 正在播的那首、播放位置和播放器状态；队列为空时 `item` 是 `null` |
| `play` | 写 | 播放一组歌曲 id、一张专辑、一位艺人或一个歌单；什么都不传就是继续播放 |
| `pause` / `next` / `previous` | 写 | 暂停、下一首、上一首 |

**只查资料库，不查 Apple Music 曲库。** `MPMediaQuery` 只看得到用户买过、同步过或者自己加进资料库的内容。搜整个 Apple Music 曲库要走 MusicKit，那是 Swift-only 的接口，还要给 App ID 另开一项服务，这一版不做。工具说明和内置 skill 里都写明了这一点，免得智能体许诺「什么歌都能放」。

**为什么用系统播放器。** `systemMusicPlayer` 就是「音乐」App 自己的播放器：问「现在放的是什么」得到的是用户真在听的那首，开始播放之后切走或关掉本 App 也不会停。代价是 `play` 会替换用户在「音乐」里原有的播放队列，所以四个播放控制操作算写操作，受写入策略管，尽管资料库本身一个字节都没改。

**`play` 只收 id，不收名字。** 要先 `search` 再拿 id 来播：同名专辑、重名歌单很常见，原生侧不替调用方挑（§4.5）。`search` 每种 `kind` 只比一个字段，因为一个 predicate 只能指定一个属性，多个 predicate 之间只有「与」；要做「标题或艺人」就得自己合并两次查询并决定顺序，那已经是在排序了。

**维护时要知道的坑：**

- persistent id 是 64 位整数，经常超过 2^53。两个方向都用十进制字符串传，传数字会被拒绝并说明原因——四舍五入之后的 id 可能恰好是另一首歌。
- 专辑和艺人在 MediaPlayer 里不是独立记录，只是歌曲的分组，id 和名称取自分组的代表曲目（`albumPersistentID` / `artistPersistentID`）。歌单是独立记录。
- `songs` 里只要有一个 id 找不到，整次 `play` 就报错并列出这些 id，不会只播找得到的那几首。
- 确认框和使用记录里的摘要取自真实记录（歌单的真名和曲目数），不用调用方传来的文字；摘要只含名称和数量，不含句子（§5.4）。
- `prepareToPlay` 的回调来自另一个进程，可能永远不来（模拟器、用户删掉了「音乐」App、未下载的歌遇上断网）。所以有 20 秒时限，到点报错。**这时队列已经被替换了**，错误消息里写明了这一点；因为返回的是错误，这一次不会进使用记录。
- 开了随机播放时结果里不带 `first`：第一首由播放器决定，按队列顺序报第一首就是把猜测当事实。
- `next` / `previous` 的结果只带切歌之前那首（`from`）。播放器要过一会儿才更新 `nowPlayingItem`，当场读会读到旧的，所以让调用方再调一次 `now`。
- `currentPlaybackTime` 可能是 NaN，而 `NSJSONSerialization` 遇到 NaN 会抛异常，所以 `position` 不是有限数时给 `null`。
- **`played` / `paused` / `skipped` 的意思是「命令发出去了」，不是「现在有声音」。** 队列为空时不带目标的 `play` 照样返回 `played: true`，只是 `item` 是 `null`；渲染出来的那句话会说「让音乐播放了，但看不到队列里有东西，用 `now` 确认」。没有在原生侧改成拒绝：队列空不空是播放器的事，而且「音乐」App 自己的队列里可能有本 App 看不到的东西。
- 模拟器里资料库是空的，也没有「音乐」App：`search` 返回空，`playlists` 返回 5 个系统自带的智能歌单（曲目数都是 0），`now` 是 `item: null`，带 id 的 `play` 报「找不到这个 id」。真正的播放路径只能在真机上验证。

#### weather：某个坐标的天气和预报（WeatherKit）

三个操作，全是只读：`current`（此刻）、`hourly`（接下来 N 小时，默认 24，最多 240）、`daily`（从今天起 N 天，默认 7，最多 10）。每个都必须带 `latitude` / `longitude`。

**它不读用户的位置，所以没有系统权限、没有开关、也不记使用记录。** 「这里的天气」是两步：先 `location` 拿坐标（那一步才要授权），再拿坐标来问。地名也不收 —— 把地名解析成坐标就是在几个候选里替调用方挑一个（§4.5），那是 `location geocode` / `maps search` 加上模型自己的事。好处是「成都明天下雨吗」这种问题一点隐私成本都没有。

和 alarm 一样是 Swift 实现、ObjC 转发：WeatherKit 没有 ObjC 接口。`DshWeatherBridge.h` 是 ObjC 这边拥有的协议，`WeatherProvider.swift` 只管问框架、把答案摊成字典；参数校验、截到调用方要的条数、所有拒绝措辞都在 `caps_weather.m`。和 alarm 的一处不同：失败传的是 `NSError` 而不是一句话，因为下面那种失败只能靠 error domain 认出来。

维护时要知道的几件事：

- **出处是许可条款的要求。** 每个结果都带 `attribution: {service, legalURL}`（取自 `WeatherService.shared.attribution`），工具渲染出来的最后一行就是它，工具说明也要求模型转述预报时保留这一行。出处取不到时整次调用失败，数据不会不带出处地出去。改渲染时别把这一行弄丢。
- **单位写死，不跟系统地区走**：°C、km/h、hPa、km、mm，随结果里的 `units` 一起出去。读数的是模型，它不知道这台手机设的是摄氏还是华氏。湿度、云量、降水概率是 0–1 的小数。
- **时间全是 UTC，结果里 `timeZone: "UTC"` 明说。** WeatherKit 的答案不带时区（`WeatherMetadata` 只有 `date` / `expirationDate` / `location`），要写成预报地点的当地时间就得自己拿坐标反查时区，那是拼出来的，第一版不做。副作用：`daily` 每一天的 `date` 是当地零点对应的 UTC 时刻，东半球看上去早一天（上海的 11 日是 `…10T16:00:00Z`）。工具说明和渲染的表头都提醒了这一点。
- **`condition` 是 WeatherKit 的枚举原名**（`mostlyCloudy`），不对照成别的词表；`conditionDescription` 是框架给的那句话，语言跟系统语言走。
- **条数只截不挑。** `hourly` 向框架要「现在到 N 小时后」这个窗口，窗口两头的半个小时算不算由框架定，可能多回一条；`daily` 用框架默认的十天。`caps_weather.m` 按时间顺序留前 N 条，`total` / `truncated` 如实报。超出上限的 `hours` / `days` 是拒绝而不是悄悄夹到上限 —— 要 30 天却只拿到 10 天的模型会去描述一个它没见过的月份。
- **没开通时的失败长得像网络抖动。** App ID 没开 WeatherKit（能力和 App Service 两处）或包里没有 `com.apple.developer.weatherkit` 时，每次请求都从一个私有 daemon 域（`WeatherDaemon.WDSJWTAuthenticatorServiceProxy.Errors`）失败，文案只有「操作无法完成」。模型照着转述成「稍后再试」会把用户送进死循环，所以 `caps_weather.m` 只认这一种（domain 或描述里有 `jwt` / `authenticat`），在前面加一句「这个版本还没开通天气，不是用户能打开的开关，重试没用」，后面仍带框架原文。其他错误一律原样透传，不另造分类。
- **没做的**：天气预警、分钟级降水、历史对比、`precipitationAmountByType`。`DayWeather.precipitationAmount` 从 iOS 18 起被标为弃用（部署目标升到 18 时会有警告，届时换成 `precipitationAmountByType.precipitation`）。
- **验证状态**：**没开通，所以一次真数据都没拿到过。** 模拟器上跑到的只有上面那条拒绝路径（§7.5）：约 1.5 秒后返回「这个版本还没开通天气」加框架原文。要拿到真数据，得先在开发者后台给 App ID 开通 WeatherKit（能力和 App Service 两处），在 `app/project.yml` 的 entitlements 里加上 `com.apple.developer.weatherkit: true`，再重新生成描述文件。**开通之前，能力页上天气那一行写的「始终可用」是不成立的** —— 要么先开通，要么发版前把这一行拿掉。

## 4. 授权模型

### 4.0 一个必须先知道的硬事实：iOS 的日历权限没有"只读"

iOS 17 起 EventKit 的权限是两档，**都不是只读**：

| 档位 | 能做什么 | 用途描述 key |
|---|---|---|
| write-only | 只能创建事件，**读不到任何东西**，连自己刚创建的也读不到 | `NSCalendarsWriteOnlyAccessUsageDescription` |
| full access | 读 + 写 + 删 | `NSCalendarsFullAccessUsageDescription` |

所以**要读就必须 full access，而 full access 同时把写和删也给了**。这条决定了下面整个模型：系统层面没有"让它看但不让它改"这个档，这件事只能由应用层自己兜。

（新建事件走 `EKEventEditViewController`，它只要"仅添加"那一档就够，不必拿到完整读权限。见 §4.2；曾以为它完全不要权限，实测推翻了，见 §7.3。）

### 4.1 一层：iOS 系统权限就是唯一的门

决定：**系统权限给了之后，应用层不再按调用方设授权门。**

注意这是对事实的承认，不是把插件当成服务对象（§1.1）：能力是做给智能体的，而插件恰好也够得到，按调用方拦截又守不住（§2.2、§5.3.1）。

```
iOS 系统权限  →  授给宿主 App，一次，系统弹窗
                  给了之后：本体和插件都直接能用，不分调用方
                  要撤销：设置 → 隐私与安全性 → 日历 → Fish Pocket
```

理由：

- §2.2 已经证明按调用方授权守不住（`ctx.root` 一行就穿），所以插件专属的门本来就是假的。
- 合并之后剩下的"全 App 能力开关"**和系统权限重合了**。用户在系统弹窗上同意的就是"Fish Pocket 可以读我的日历"，App 里再放一个开关，是让他为同一件事表态两次——多数人会觉得是 bug，而不是保护。
- 省下 `CapabilityStore`、授权 sheet、开关页，第一期小到能在真机上尽快验证通道。

**代价，说清楚：**

| 丢了什么 | 实际影响 |
|---|---|
| App 内的一键关闭 | 要去系统设置关。好处是那里关掉是真关掉（系统级），比我们自己的开关更可信 |
| 读写分档 | 系统层面本来就没有（§4.0）。读写之分只能靠应用层——见 §4.2 |
| 事前决策点 | 只剩"装不装这个插件"。所以安装页的警告必须加重，见 §4.1.1 |

这个决定有参照：同类产品 OpenMinis 的权限档位默认值就是"不问直接用"（§9.1）。

**不可逆性要记一笔**：一旦发布成"插件无门槛可用"，以后再加门就是破坏性变更（已装的插件会突然失效）。便宜的保险是**现在就把形状留好**——所有调用都过 addon 里的同一个分发器，分发器里留一个 policy 判断点，一期恒定放行。将来要收紧，改那一处，不动任何调用方。

那个判断点的形状**按三档设计**，不要设计成布尔开关：`bypass`（默认）/ `askOnce`（本会话内问一次）/ `notAllowed`。这是 OpenMinis 的档位（§9.2），比开关实用——`askOnce` 读写都适用，而且用户收紧时不必在"全开"和"全关"之间二选一。一期只实现 `bypass` 这一档的行为，但判定函数的签名和存储键按三档来。

### 4.1.1 唯一的事前决策点：插件安装页

去掉应用层的门之后，用户能守住的边界只剩一个：**装不装这个插件**。所以这一处的文案必须加重。

现在插件安装确认的文案是「插件在本机以你的权限运行。请确认你信任它的来源」（`docs/webui/settings-plugins.md` 的 `installTrust`）。接入本机服务后补成：

> 插件在本机以你的权限运行，**包括你已授权的本机数据（日历、提醒…）**。请确认你信任它的来源。

这不是形式。它是整条链上唯一一次用户能在"代码进来之前"说不的机会。

### 4.2 能力（scope）划分

```
calendar.read          calendar.write
reminders.read         reminders.write
notifications.post
motion.read
health.read.<type>     # steps / sleep / heartRate / workout / bodyMass …逐类型
location.read.coarse   location.read.precise
contacts.read
```

这些**不再是授权单位**（授权只有系统权限那一层），而是：

- addon 分发器的分发单位，和工具的分组；
- §4.1 那个"留好形状"的 policy 判断点将来要认的键；
- 审计记录里的字段。

命名仍按读写分开，因为读写在应用层要区别对待（§4.3），而且健康要逐类型（"读健康"太粗，步数和心率不是一个量级）。

### 4.3 读写之分只能靠应用层，而写有三个方案

§4.0 说了：系统给的是 full access，读写一起来。所以"智能体能看我的日程但不会乱改"这件事，系统不管，只能我们自己兜。三条路：

| 方案 | 强度 | 代价 |
|---|---|---|
| **① 不提供写工具** | 一期的做法。引擎侧只注册读工具，没有写的入口 | 只防误用，不防恶意——插件能直连 addon（所以 addon 的能力白名单必须拦住未实现的写） |
| **② `EKEventEditViewController`** | **最强**。弹系统原生的事件编辑器、预填内容，用户点"添加"才落库。插件无法替用户点，不可伪造 | 只适合**新建**。改和删现有事件不适用（而且要先读到它）。批量会弹很多次。**需要权限**（"仅添加"那一档就够）：没有的话这个跨进程编辑器起来即自毁，见 §7.3 |
| **③ 原生一次性 grant** | 强。Swift 侧弹自己的确认框 → 签发一次性、绑定这次操作摘要、短时效的 grant，密钥只在原生侧 | 要自己做确认 UI；批量需要合成一次确认 |

**二期实现时，③ 里的"签发 grant"这一步被证明是多余的，去掉了。**

grant（一次性令牌、绑操作摘要、短时效）解决的是**决策和执行被分开**时的问题：
决策结果要穿过一段不可信的地带再回来执行，所以需要一张不可伪造、不可重放、
会过期的票。但实际实现里这两件事根本没分开——addon 调桥、**同步等用户答复**、
拿到答复就地执行，中间没有任何东西经过 JS。没有地带要穿，就没有票要签。

所以最终形态是：`DshNativeBridging` 协议 + `bridge.m` 一个槽位 + Swift 侧的
`NativeBridge`。强度和带 grant 的版本完全一样（决策始终没离开原生侧），但少了
密钥管理、时效判断和重放检查三块代码。

新建事件仍然优先走 ②（`EKEventEditViewController`），因为它比我们自己弹的框更强：
那是 Apple 的界面和 Apple 的按钮。提醒事项没有对应的系统编辑器（EventKit 的编辑器
只管事件），所以它的三个写操作都走 ③。

②这次查文档时看起来像个意外收获：`EKEventEditViewController` 似乎**完全不需要日历权限**就能让用户创建事件。对"帮我把周三下午两点的产品评审加上"这种最常见的助理场景，它同时解决了确认和权限两件事，而且用户看到的是系统界面，可信度最高。

**但"不要权限"那半句后来被实测推翻了**（§7.3）：这个编辑器是跨进程扩展，没有权限时它会起来然后立刻自毁，代理回调永远不来——调用方不是收到报错，是**永远挂着**。现在它要过"仅添加"那一档的检查，比读宽，但不是不检查。"用户看到的是系统界面，插件替不了他点"这半句仍然成立，②依然是最强的写入路径。

**三期之后这整段又改了一次方向，记在 §4.3.3。** 上面说的"②和③"现在不是默认，而是用户把写入设成「每次确认」时才走的那条路。

### 4.3.1 确认框：把可信信息放主位

框里有两种信息，强度完全不同：

- **操作内容**不可伪造——它就是即将执行的东西（"在『工作』日历新建：周三 14:00 产品评审"）。
- **调用方**可伪造（§2.2）。

所以操作内容是主体、大字、完整列出；调用方只作辅助行，措辞不能暗示它验证过。写「来自：插件 foo（自报）」，不要写「插件 foo 请求」。

### 4.3.2 桥上的每一次等待都必须有结果

addon 调到 `NativeBridge` 之后是**同步等**的：Node 那边是一个没 settle 的 Promise，插件停在 `await` 上。所以界面不答复 ≠ 什么都没发生，而是**插件永远卡住**。挂死比报错坏得多——报错至少能说给用户听。

这不是假想的风险，一期到三期的模拟器验证里就撞上了（§7.3）：

- `EKEventEditViewController` 是**跨进程扩展**（`EventKitUIRemoteUIExtension`）。没有日历权限时，它会起来、ready，然后立刻 `interruptionHandler` 自毁，`didCompleteWith` 代理回调**永远不来**。
- 当时 `create` 还跳过了授权检查——理由是"这是 Apple 的界面，不需要权限"。这个假设是错的，而错误的代价不是一个报错，是一次挂死。

所以定两条：

1. **要用户点的操作，先确认拿得到权限。** 新建只需要"仅添加"那一档（iOS 17 的 `writeOnly`），所以它过的是 `with_add_access`，比读宽、但不是不检查。
2. **每个等待都配看门狗。** 界面上过屏之后又没了、却没人答复，就替它收尾，并且如实说是"界面没了"而不是"用户取消了"——这两件事对用户的意思完全不同。

### 4.3.3 默认不确认：写入策略交给用户，一项一档

决定：**写操作默认直接执行，不弹任何界面。**「每次确认」降级成用户可以自己打开的一档。

这推翻了二期的默认值，理由是体验：最高频的请求就是"帮我加个日程"，而每一次都要用户再点一遍 Apple 的编辑器，等于把一句话的事变成一次操作。参考实现 OpenMinis 是直接 `saveEvent:` / `removeEvent:`，没有任何逐次确认（§9）——所以**逐次确认是产品选择，不是硬性要求**，两个方向都走得通。

它换成了 §4.1 当初特意留的那个 policy 判断点，按三档设计、默认 `bypass` 的那个。现在把它放出来：

| 档 | 行为 | 对应 OpenMinis |
|---|---|---|
| **直接执行**（默认） | 写就写了，只进使用记录 | `bypass` |
| **每次确认** | 新建弹系统事件编辑器，其余弹原生确认框——二期做的那一套 | `askOnce` 的更严版本 |
| **不允许** | 拒绝写，读照常 | `notAllowed` |

**按能力存，不按调用方**——§2.2 settled 过，调用方分不开，一个"只限插件"的开关会是假承诺。

落地时定下来的几条：

1. **判断点在桥上，不在各个能力里**（`DshNativeConfirmWrite`）。和权限判定、审计记录同一个位置、同一个理由：唯一一条路，后加的能力绕不过去（§9.3）。
2. **读不到的值按最严处理。** `UserDefaults` 里存的不是这三个值之一时，当作「不允许」。存储坏了不是放宽一道门的理由——这和"没设过就是 0（直接执行)"不矛盾：没设过是已知状态，读不懂不是。
3. **直接执行档不需要界面。** 以前就算不弹框也得先拿到 window，拿不到就失败；现在只有「每次确认」档才需要桥。
4. **能力表多一列 `writeOps`**，标明哪些操作会改用户自己的数据。`notify` 故意留空——本地通知是 App 自己的提醒，不在用户数据里留东西，不是这个策略要管的"写"。只读的能力在界面上根本不显示这个开关。
5. **被策略拒绝的消息要说清楚是谁设的、在哪改。** 模型会读给用户听，而用户很可能已经忘了自己设过。

**代价，说清楚：** 默认档下，任何一个装进来的插件都能静默增删改用户的日历和提醒，和引擎本体无从分辨。这正是 §5.4 那张使用记录从"有用"变成"必需"的时刻——它是用户唯一能事后查证的地方，所以"被拒绝的写绝不能记进去"那条（§7.3 的 bug 3）在这之后更要紧了。

### 4.4 和引擎已有机制的关系

- **会话权限预设**：`read-only` 会话不得使用任何 `*.write` 能力，`workspace-write` 同样（本机服务不在工作区内）。只有 `full-access` 会话 + 已授权 + 当次确认，写操作才成立。实现上在 `tools/pre-execute` 里拦，或 `ctx.tools.restrict()` 直接把写工具从该会话的工具表里摘掉。
- **提醒 vs todo vs schedule**：三者不要互相同步，职责分开说清楚——DSH 的 todo 是**本轮任务清单**（给模型看的），`dsh-schedule` 是**定时触发 dsh 自己**，系统提醒是**给用户看的待办**。智能体可以把 todo 写成系统提醒，但不做双向同步（会打架）。
- **`when` 条件注册（引擎 0.2.2 新增）**：`ctx.tools.register(definition, { when })` 可以按步决定一个工具是否参与。将来做权限收紧时值得用上——没有系统权限时让工具**根本不出现在模型的工具表里**，比现在"工具总在、调用才报错"干净，也省掉模型一次无效调用和一轮解释。它不能替代 addon 里的判定（插件可以绕过 JS 层直连 addon），是模型侧的补充。
- **审批 UI**：写操作的确认**不复用**引擎已有的 `approval/request` waterfall，有两个原因。一是粒度：它只能说"工具 X 请求越权执行"，表达不了"要在『工作』日历新建周三 14:00 的产品评审"这种操作摘要，而摘要恰恰是确认框里唯一可信的信息（§4.3.1）。二是强度：它的决策结果回到 JS 侧，插件可以不等审批直接调 addon——**决策必须留在原生侧**才算护栏。所以写确认由 addon 同步等 `NativeBridge.swift` 的回调，不经 JS。

### 4.5 只转发，不替调用方解释

原则：**原生侧是 Apple SDK 的桥，不是它的解释层。** 不参与任何 SDK 的内部逻辑，不替调用方从多个答案里挑一个、过滤、或改写。

理由不只是洁癖，是维护量。每一条「我们替它判断一下」的规则，都要跟着 Apple 的行为、跟着地区、跟着语言一路打补丁，而这些补丁没有尽头。

**判断一段代码该不该留，分三类：**

| 类 | 是什么 | 例子 | 留不留 |
|---|---|---|---|
| ① | **必填参数的默认值**。Apple 要求必须传，我们给一个合理的，调用方能覆盖 | `vision.text` 默认认中英（Vision 原厂只认英文，不设等于中文全废）、`location.current` 默认粗精度、`maps.eta` 默认驾车、`calendar.create` 没给 end 就 +1 小时 | **留**。一次性，零维护 |
| ② | **选哪个 Apple API 来回答这个问题** | 地名解析用 `CLGeocoder` 而不是 `MKLocalSearch`（后者排的是附近商户） | **留**。做一次之后零维护 |
| ③ | **替调用方从多个答案里挑、过滤、或改写** | `places.firstObject`、`confidence < 0.1` 丢掉、自己写的「这个结果像不像答案」 | **砍** |

**第三类的代价是实测出来的。** 地名解析那一轮（§7.4）：`MKLocalSearch` 从中国区查「San Francisco」得到一家面包店；换成 `CLGeocoder` 之后变成云南普洱一个镇，两端解析到同一个地方，ETA 报出「1 米 1 秒」。

当时的修法是加一条「解析结果得和问题对得上」的检查。**它确实修好了那个 bug** —— 复验时 San Francisco 被正确拒绝。但它是我们自己发明的字符串相似度规则，而且**上线前就已经打过一个补丁**：「北京市」对上英文的「Beijing」字面毫无交集，正确答案被判成错的，只能再加一个 `preferredLocale` 压住。接下来还有缩写（SF、NYC）、音译、别名、行政区划改名……这正是第三类的形状：能跑，但你要养它一辈子。

**所以根子不是「用哪个解析器」，也不是「检查做得够不够好」，是我们一开始就不该挑。**

落地：

- `maps.eta` / `maps.route` **只收坐标**。想从名字出发的调用方先调 `maps.search` 或 `location.geocode`，自己看一眼再决定。多一次调用，换来的是「云南普洱」这种结果直接摆在模型眼前，而不是藏在一个 1 米的 ETA 背后——而模型恰恰最擅长一眼看出「这不是我说的那个 San Francisco」。
- `location.geocode` / `reverse` **返回全部候选**，按地理编码自己的顺序，字段形状和 `maps.search` 对齐。
- `vision.classify` **没有置信度阈值**。Vision 会报上千个标签、大半分数接近零，砍尾巴很顺手，但任何一刀都是我们凭空定的数，而「0.09 在这张图里算不算相关」是调用方对这张图的判断。

**条数上限不算第三类。** `maps.search` 的 15 条、`vision` 的 25 个标签，管的是回复的大小，不是哪个答案好——所以它们保留，但必须如实报 `total` 和 `truncated`，让调用方知道自己只看到了一部分。

## 5. 实现路线

### 5.1 走 native addon（曾推荐 waterfall，被引擎的 allowlist 否掉了）

| | 做法 | 结论 |
|---|---|---|
| **A** | **native addon（ObjC），像 `dsh_git` / `dsh_image` 一样静态链进 App，引擎 `process._linkedBinding('dsh_ios_native')`** | **采用。** 同进程直连，与现有 addon 一致，有现成脚手架。**OpenMinis 走的也是这条** |
| B | Swift 起本地 HTTP 服务，引擎 `fetch` 调 | 备选。全 Swift 好写 UI，但要新开端口和认证，还反了现有方向（现在 Swift 是客户端） |
| C | 走已有的 `$events` waterfall：引擎发请求事件，Swift 执行并回结果 | **走不通**，见下 |

**C 为什么走不通**（查证 `@deepseek-ai/dsh@0.2.1-rc.4`）：

转发给客户端的 Host 事件是一张**硬编码 allowlist**——`dsh-api-remotes/lib/index.js` 里的 `API_REMOTE_FORWARDED_EVENTS`，注释写明它是"这个 allowlist 唯一的家"，`approval/request` 和 `user-questions/request` 都在里面。而 Gateway 只接受**唯一一个** Remote Event source。所以：

- 想加自己的 waterfall 事件 → 只能改引擎文件 → **`CONTRIBUTING.md` 明令禁止**（"不改引擎文件"）。
- 复用 `approval/request` → 只能返回 `allowed-once | rejected`，拿不到数据。
- 复用 `user-questions/request` → 语义是问用户问题，在原生界面会渲染成提问卡。
- 插件自己的 **stream RPC** 不受 allowlist 限制（`session/follow` 就是这么做的），但要用 TC39 装饰器声明，而我们的插件是无构建步骤的 `.mjs`，Node 24 不支持装饰器语法。

**选 A 的理由**（除了"C 不可行"）：

1. **不依赖原生客户端在线**。这是比 C 更强的地方：agent 在后台跑任务时想发一条通知，addon 直接就能发；C 则要求 Swift 的 WebSocket 还连着。
2. 不碰引擎的任何内部机制，不会因引擎升级而坏。
3. 脚手架齐全：`native/` 下已有三个 addon，`project.yml`、构建脚本、`process._linkedBinding` 的取用方式（`engine/runtime/git/binding.mjs`）都是现成样板。

**A 的两个代价，以及怎么处理：**

- **要写 ObjC。** 不可避免。`native/image/image.c` 是现成的 N-API 样板，照它的结构写 `.m`。
- **需要 UI 的操作怎么办**（授权弹窗、写确认）：addon 和 Swift 在同一个进程，ObjC 可以 `dispatch_async` 到主队列调用 Swift 的 `@objc` 单例，Swift 弹 UI，再用 N-API 的 ThreadSafeFunction 把结果送回 JS。**决策仍然留在 Swift**，所以 §5.3 的写侧强边界不受影响——JS 伪造不出 Swift 的确认结果，因为 addon 等的是 Swift 的回调。
- 由此得到一条**硬性实现约束**：**addon 的写操作 API 必须自带确认，不许提供绕过确认的变体。** `_linkedBinding` 对任何 JS 都可见，插件可以直接调 addon；这没问题（按 §4.1 的模型，它拿到的权限和老实调用一样），但前提是 addon 里没有一个"免确认写入"的后门。

```
                            #    examples 的目录本身就是在招手
```

**能力清单只有一张表。** 设置页列的、N-API 分发用的、判定一次调用合不合法的，都是 `ios_native.m` 里那个 `CAPABILITIES` 数组：`DshNativeCapabilityList()` 是它的只读视图，经 bridging header 给 Swift。界面不许自己维护一份拷贝——两份清单迟早对不上，而对不上的那条缝就是绕过（§9.3）。页面的中文名和说明按能力 id 查，**查不到就显示 id**，所以原生加了能力而忘了加文案，页面会少个名字，但不会漏掉这项能力。

零期的 Swift 只有这一页：三个能力本身都不需要 UI。`NativeBridge.swift` 是一期（日历授权、写确认）才需要的那座桥。

**数据流**（以第三方插件读日历为例）

```
调用方（本体工具或第三方插件，走同一条路）
  ctx.iosNative.calendar.list({from, to})
  └─ caller.mjs：尽力归因 → callerClaim（只打标签，不判定）
  └─ binding().invoke('calendar.read', 'list', args, callerClaim)
       └─ addon（同进程，任意线程）
            ├─ 能力判定键 == 分发键，同一张表（§9.3 的教训）
            ├─ 系统权限 notDetermined → dispatch 到主线程请求（系统弹窗，文案来自 Info.plist）
            ├─ 系统权限 denied → 回 need-system-permission
            │                     （引擎转人话让智能体说出来；App 内给跳转入口）
            ├─ policy 判断点 ——— 一期恒定 bypass，是 §4.1 留的收紧位置（三档形状）
            ├─ 写操作 → dispatch 到 NativeBridge.swift 弹确认，等回调
            └─ 执行 EventKit → 记一条审计 → ThreadSafeFunction 回结果
  └─ 调用方拿到结果
```

一期没有我们自己的授权 sheet——系统弹窗就是全部。所以**那次弹窗的文案（Info.plist）承担了全部告知责任**，见 §6.2。

两个实现细节：授权前若已 fetch 过，拿到权限后要 `EKEventStore.reset()` 才读得到数据；系统权限一个 App **一生只弹一次**，拒绝后不再弹，只能引导去设置——所以别在用户还不知道发生什么的时候触发它。

### 5.3 安全边界的真实强度（必须讲清楚）

| 场景 | 实际强度 |
|---|---|
| 没给系统权限 | **挡住**，iOS 挡的，最硬的一道 |
| 用户想收回 | **能**，去系统设置关。系统级撤销，比我们自己的开关更可信 |
| 给了权限后，插件读日历 | **不拦**，这就是本方案的明确语义：权限给的是这个 App，含它装的任何插件。事前靠安装页警告（§4.1.1），事后靠审计（§5.4） |
| 插件冒充本体 | **不适用**。没有"本体专属"的权限可冒充，§2.2 那个攻击失去了目标 |
| 插件绕过 JS 网关 | **绕得过，但无所谓**。`_linkedBinding('dsh_ios_native')` 对任何 JS 可见，插件可以直连 addon——拿到的权限和老实调用完全一样（§4.1 的模型不按调用方分）。前提是 addon 里没有免确认的写后门 |
| 表里没有的操作 | **挡住**。能力白名单——不是授权门，是"没实现的操作一律不执行" |
| 插件写/删日历或提醒 | **看用户设的写入策略**（§4.3.3）。默认「直接执行」时不拦——和读一样，权限给的是这个 App。用户把那一项设成「每次确认」后才每次停下来，而那道确认在原生侧，插件替不了他点 |

一句话：**门就是 iOS 那一道，加上用户自己为写操作设的那一档**。应用层不假装有按调用方的粒度，省下的复杂度换成了"把唯一那次系统弹窗、唯一那个事前决策点和使用记录做好"。

#### 5.3.1 封锁不可行，这一点现在有实测数据

「把 addon 藏起来，只留给本体」听上去像个办法。2026-11-10 在模拟器上试过，不行：

| 试法 | 结果 |
|---|---|
| 本 realm `delete process._linkedBinding` | 挡住 |
| 本 realm `delete process.binding` | 挡住 |
| **两个都删之后，`new Worker(code, {eval: true})` 里** | **两个把手都在，照样拿得到 addon** |
| Worker 里 `require('internal/bootstrap/realm')` | 够不着（Cannot find module） |

插件写一行 `new Worker` 就是一个新 realm、一个新 `process`，我们在主 realm 删掉的东西在那里原封不动。要堵就得连 `worker_threads` 一起包——而引擎自己的 `child_process` 就是用 Worker 实现的，还做着模块重定向，还开着 `--expose-internals`。**在沙盒里再造一个沙盒，漏一个口子我们永远不会知道。**

所以不做这件事，也不假装做了。要做到按调用方的真隔离，得把第三方插件挪进独立 isolate 并代理它的全部 `ctx` 访问（`ctx.root` 这类逃逸口也要一并堵掉），那是引擎级改造，不在本文范围。

**反过来的推论同样要记住：既然关不上，`ctx.iosNative` 就不该为了"劝退"而藏起来。** 藏它不关门，只会把老实的插件赶到没署名的那条路上——cordis 读不出名字，使用记录里调用方那一栏就是空的。审计会变差，不会变好。

### 5.4 审计存哪

没有授权记录要存了（授权状态由 iOS 持有，`EKEventStore.authorizationStatus` 随时能问）。只剩审计：

```
audit: { capability, op, callerClaim, at, summary? }   # callerClaim = 自报的调用方，不可信
```

存原生侧（`UserDefaults` 够用，不含秘密）。**不要存引擎侧**：引擎侧的文件，插件自己就能改。

`callerClaim` 这个名字是故意的——在代码里就能看出它不可信，别让后来的人拿它做判定。审计是环形缓冲（留最近若干条，不是日志系统），写操作连操作摘要一起留，这样用户事后能看出"那个会议是谁删的"。

去掉能力开关之后，审计是用户**唯一**能看到"这个 App 碰了我哪些数据"的地方，所以它从"锦上添花"升级成了必要项。

**落地时定下来的四条**（`audit.m` / `ios_native.m` / `NativeAuditView.swift`）：

1. **记录点在分发器里，不在各个能力里。** 和权限判定同一个位置、同一个理由：那是唯一一条路，后加的能力没法绕过它。
2. **只记 `systemPermission` 非空的能力，且只记成功的。** 这张表回答的是"什么碰到了我的数据"，把 `device.info` 和每次 `speak.say` 都记上，只会把用户真正要找的那条日历读取挤出环形缓冲。
3. **摘要由能力自己给，走结果里的 `auditSummary` 键**，分发器取走它、记进审计，再把它从交给 JS 的结果里删掉——它是给用户的审计列表看的，不是给模型看的。
4. **摘要必须语言中性。** 它会原样显示给用户，而 App 是三语的、原生这几个文件不是。所以摘要只放日期、数量、事件标题、用户自己写的文字，不放句子；"日历 · 读取事件"这类行文案由 Swift 按 `capability` + `op` 自己拼。

`callerClaim` 在界面上也不装作可信：本体自报的 `dsh` / `root` 显示成「智能体」，插件显示它自报的包名，没报的显示「未知来源」，页脚直说"调用方是自己报的名字，不能当证据：插件可以把自己报成引擎本体"。

### 5.5 授权弹窗只在用户自己走进来时出现

决定：**能力在没拿到系统授权时直接拒绝调用，不自己弹框。系统授权框只在用户于「本机能力」页点「开启」时出现。**

这不是 §4.1 否掉的那个"应用层开关"。门还是只有一道，还是系统那道；变的只是**这道门在什么时机被推到用户面前**：

| | 改之前 | 改之后 |
|---|---|---|
| 弹窗由谁触发 | 碰巧第一个调用的插件 | 用户自己点「开启」 |
| 用户当时在看什么 | 不一定，可能在聊别的 | 一张列清楚每项能力是什么的页面 |
| 没授权时的调用 | 弹框，然后等 | 直接拒绝，附一句能转述的话 |

三个理由：

- **弹窗是一次性的。** iOS 对一个 App 一生只问一次。没人应答时 App 被重启，后续请求直接拿到「已拒绝」，只能回系统设置救（§7.1 的教训）。把这唯一一次花在"用户没在看"的时刻，是拿用户的权限去赌。
- **插件触发的弹窗没有上下文。** 用户看到"Fish Pocket 想访问你的日历"，但不知道是谁想要、为什么现在要——而 §2.2 已经证明我们**没法**在框里诚实地写出调用方。与其写一句可伪造的来源，不如根本不在那个时机问。
- **拒绝比弹框更可转述。** 拒绝消息是写给模型的，模型会用用户的语言说出来："你还没开日历，可以去侧边栏的「本机能力」里打开。" 这比一个突然出现的系统框更像一次解释。

代价和应对：

- **入口不好找，能力就永远开不起来。** 所以它在侧边栏有自己的一行（`DrawerView.capabilitiesRow`），不只藏在设置里。
- **拒绝消息里不能引用界面上的标题。** addon 那几个文件不翻译，而界面是三语的；写死「本机能力」四个字迟早和屏幕上的字对不上。所以消息描述位置（"the app's sidebar"），让模型自己用用户的语言说。

实现上只有一个入口会弹框：`DshNativeRequestPermission`（`ios_native.m`），它读的是和分发器同一张能力表，表里没有的 `systemPermission` 会被明确拒绝，而不是悄悄什么都不做。能力侧对应改成 `DshEventKitRequireAccess` / `require_authorization`——名字从 Request 改成 Require，就是为了让"这里不会弹框"这件事在调用点上看得见。

### 5.6 不对第三方承诺，调用形状也不保证稳定

决定：**本机能力不是公开 API。** 能力名、操作名、参数形状都可以随版本改，不作任何兼容承诺，文档里也不以"给插件开发者"的口吻描述它。

这和 §5.3 并不矛盾，两件事要分开说：

- **够不够得到**：够得到，而且拦不住（§5.3.1 有数据）。这是事实陈述，不能软化。
- **承不承诺**：不承诺。这是我们的选择。

**为什么是这个选择：** Agent 靠 `SKILL.md` 跟进——能力改名，改一行文档就行，下一轮对话它就知道了。硬编码的插件做不到，它会直接断。对外保证调用形状，等于把「能力表随时能重排」这个自由永久交出去，而现在这个阶段，这个自由比插件那点便利值钱得多：这张表这一周就重排过三次（砍掉 NLP 两个废操作、`eta` 改成只收坐标、`classify` 去掉阈值），每一次在有兼容承诺的世界里都是破坏性变更。

**将来真要做硬编码 SDK 支持**，就得单独维护一套版本化的 API 协议——协商版本、留弃用期、写迁移说明。那是另一件事，留着以后再说。

**有两件事绝对不能因此变软**，恰恰相反，正因为门关不上，它们才是承重的：

1. **安装页的警告**（§4.1.1）。它是整条链上唯一一次用户能在"代码进来之前"说不的机会。
2. **使用记录**（§5.4）。它是唯一的事后凭据。

把「我们不推荐插件用」当成放松这两样的理由，是拿一个做不到的承诺去换真实的防护。

## 6. 合规

### 6.1 HealthKit：能接，但要想清楚告知

Apple 对 HealthKit 数据有硬条款：不得用于广告或基于使用的数据挖掘，不得未经用户同意披露给第三方，不得写入虚假数据。

而这个 App 的事实是：**智能体读到的东西会发给模型服务商；第三方插件能联网。** 这两条和上面的条款撞得很正。

**但有参照说明这条路能走通**：OpenMinis 把 HealthKit **读和写都做了**（写的用例就是"拍一张饭的照片，把营养数据写进 Apple Health"）（§9.1）。所以下面这节原本的"建议一期不做"要降级为"**可以做，但要清楚自己在接什么**"——难的不是能不能接，是数据流向的告知。

如果要做健康读：

粒度上有个好消息：**HealthKit 的授权本来就是系统做的、逐类型的**，用户在系统界面上逐项勾选。这已经是比我们自己能做的任何开关都好的粒度，所以健康不需要应用层开关。

坏消息是"不让插件读健康"这件事**做不到**——理由和 §2.2 一样，应用层的调用方区分守不住。所以这是个二选一：

| 选项 | 含义 |
|---|---|
| **A. 不接 HealthKit** | 建议的第一期做法。日历 + 提醒 + 本地通知已经能撑起助理的主要场景，合规风险低一个量级 |
| **B. 接，并接受插件也能读** | 那么用途描述和 `PRIVACY.md` 必须写明这一点，让用户在系统弹窗前就知道 |

还有第三条路值得考虑：**C. 健康走"用户主动分享"，不做成工具。** 由用户在 App 里主动把健康摘要作为上下文发给智能体（像现在的相机附件那样——用户主动拍照，而不是智能体随时能开相机），引擎侧**不导出**健康服务、不注册健康工具。插件没有调用入口，智能体也不能主动查。代价是"昨晚睡得怎么样"这种主动询问要用户自己点一下。

无论走哪条，这几件照做：

- `NSHealthShareUsageDescription` 必须明说「这些数据会发给你选择的模型服务商」，不能只说"用于回答你的问题"（同 §6.2.1）。
- `PRIVACY.md` 要加一节讲健康数据的流向。

**建议：一期按 A（先把日历跑通），之后 B 和 C 都成立——B 有 OpenMinis 作参照，C 更稳。** 不再把健康当成"风险太大别碰"，而是"决定好告知方式再碰"。

### 6.2 清单与文案要同步改的地方

| 文件 | 改什么 |
|---|---|
| `app/project.yml` | 每个能力的 `NS*UsageDescription`；HealthKit 还要 capability / entitlement 和 `HealthKit.framework` |
| `app/DshIOS/PrivacyInfo.xcprivacy` | **待定，没动，见下。** |
| `PRIVACY.md` | ✅ 已改：本机数据不另存、每次现读；使用记录留在本机可查可清；日历和提醒会随对话发给模型服务商（中英两版都改了） |
| `engine/skills/ios-environment/SKILL.md` | ✅ 已改：日历和提醒两行、写操作要确认、`notify` 和 `reminders` 怎么选、被拒和「仅添加」怎么说 |
| `docs/webui/parity.md` | ✅ 已改：新增 §3.3「本项目自有扩展」 |
| `docs/webui/settings-plugins.md` | ✅ 已改：`installTrust` 文案按 §4.1.1 加了本机能力那半句 |
| `app/project.yml` + `InfoPlist.xcstrings` | ✅ 已改：日历和提醒两条用途描述，中英西三语 |

**`PrivacyInfo.xcprivacy` 为什么没动——这是个口径问题，不是代码问题。**

现在的清单里 `NSPrivacyCollectedDataTypes` 是**空的**。但这个 App 早就在把对话内容、文件内容、命令输出和相机照片发给用户选定的模型服务商了。也就是说，项目现有的口径是：**用户自己发起、发给用户自己选的服务商，不算开发者"收集"。**

日历和提醒是完全一样的形状——用户授权、用户提问时才读、直接发给用户选的服务商、不经过我们、我们不另存。按现有口径，它们同样不需要申报。

所以这里**不是"漏了日历"，而是整条口径要不要改**：

- 维持现状：一致，且有现成先例（照片走的就是这条）。
- 改成申报：那就不只是加日历，对话内容和照片也得一起申报，是整份清单重写。

这件事牵扯的是产品/法务判断，不是实现细节，所以留给人定。本次改动没有碰这个文件。

### 6.2.1 用途描述是唯一的告知渠道，所以文案是正事

一期没有我们自己的授权 sheet（§4.1），系统弹窗就是全部。那条弹窗上显示的就是 Info.plist 里的用途描述——它同时要满足两件事：**写得准确**，**用户据此作出知情决定**。

写「用于日历功能」会被打回，而且什么都没告知。草稿：

```
NSCalendarsFullAccessUsageDescription
  让智能体按你的要求查看和安排日程。为回答你的问题，相关日程内容会
  随对话发送给你选择的模型服务商。

NSRemindersFullAccessUsageDescription
  让智能体按你的要求查看和创建提醒。为回答你的问题，相关提醒内容会
  随对话发送给你选择的模型服务商。
```

**第二句是个产品选择，不是硬性要求**——这点要说清楚。OpenMinis 的同类文案只写了"让 AI agent 代你查询日程、查看空闲、创建事件"（句式统一为 *…so the AI agent can … on your behalf*），**没有提数据会发给模型服务商**（§9.1）。

所以：不写也行。写它的理由是另一个——这个 App 的数据流向和普通日历 App 不一样，用户有权在点"允许"之前知道，而不是去读没人会看的隐私政策。倾向保留第二句，但这是取舍，不是硬性要求。

（我们的文案要自己写，不照抄 OpenMinis 的——它是 GPL。）

（`NSCalendarsUsageDescription` 这个旧 key 只有链接 iOS 10–16 的 App 才需要；本项目 deployment target 是 17.0，不用加。）

| **第三批** ✅ | 通讯录、撰写页、文件、音乐、天气 | `caps_contacts.m` / `caps_compose.m` / `caps_files.m` / `caps_music.m` / `caps_weather.m` + `WeatherProvider.swift`，五个工具，能力页五行，SKILL.md 同步。设计见 §3.2，验证见 §7.5。**天气要等 App ID 开通 WeatherKit 才有数据** |

分期在执行中有三处偏离，都是有意的，记在这里免得后面的人按原表推断：

1. **本地通知（`notify`）零期就做了**，所以三期只剩 `reminders.*`，上表已改。
2. **审计从二期挪到了一期。** §5.4 说审计是"用户唯一能看到这个 App 碰了我哪些数据的地方"，而一期上线日历读之后插件就能直连 addon 读日历（§5.3 的明确语义）。排在二期意味着中间有一段用户完全查不到的窗口。审计本身很轻（一个环形缓冲 + 一个列表页），没有理由让那个窗口存在。
3. **二期的"一次性 grant"被简化掉了**，因为决策和执行根本没有分开——详见 §4.3 表格下面那段。

去掉应用层授权后，一、四期都明显变轻：一期不用做 `CapabilityStore` 和授权 sheet；四期不再是"搭一套插件授权体系"，只是**把服务导出 + 改一句安装页文案**——插件和本体走的本来就是同一条路。四期的归因（`caller.mjs`）跟着审计一起做了，边界验证插件（`engine/test/native-boundary-plugin/`）把这条路真的跑了一遍——它的用处是**证明警告说的是真的**，不是示范怎么接入（§1.1）。

一期做完就能验证最关键的假设：**Node 线程发起 → Swift 执行 → 系统弹窗 → 结果回到智能体**这条链在真机上通不通。模拟器能过不代表真机能过（`CONTRIBUTING.md` 的既有教训）。

**验证过：**

**没验证：**

- ~~真机~~ **已在 iPhone 14 Pro Max / iOS 26.6.2 上验过**（2026-11-09）：addon 加载、能力表、`device.info` 返回真实数据（6 核、64 GB 可用、iOS 26.6.2、电量 100/charging）、未知能力被拒。通知投递和语音输出的实际效果仍未确认（没等横幅、没听声音）。
- 真机上发现并修掉了一个模拟器藏住的 bug：`device.info` 第一次调用总报电量未知，而智能体通常只问一次。原因是打开电量监测用了 `dispatch_async` 就立刻读，且在 Node 线程上读 UIDevice。现在启动时预热 + 主线程读取，第一次就有值。
- 通知**真正送达**（只验证了排程成功，没等 60 秒看横幅）。
- 朗读的**声音**（模拟器音频未核）。
- 这些工具**被模型调用**的完整回合（验证走的是 addon 直调，没有发真实对话）。
- 能力页的**「已关闭」状态**：`simctl privacy` 不支持 notifications，撤销不了通知授权，所以这一档只有代码逻辑，没实跑过。

**过程中发现的两个坑**（与本次改动无关，但会绊到下一个人）：

- **debug inbox 会跳过已有 `.out` 的脚本**（`fs.existsSync(file + '.out')`）。在真机上复跑同名探针时，删本地副本没用——要删**设备上**那份，否则读到的是上一次的陈旧结果。这次就因此两度误判「修复没生效」。换个文件名是最省事的做法。
- `DSH_IOS_DEBUG` 在这次的 Debug 构建里没生效，`CONTRIBUTING.md` 说的 `<data>/debug/*.mjs` 调试通道没运行。绕过办法是 `SIMCTL_CHILD_DSH_IOS_DEBUG=1 xcrun simctl launch …`，但那次也没跑起来，原因未追。最后是直接改模拟器上已安装 bundle 里的 JS 加 `console.log` 验证的（`ctx.logger.info` 不进 `engine.log`，只有 `console.*` 经 main.mjs 的 stdout tee 落盘）。
- 授权弹窗未响应时被 `--terminate-running-process` 打断，会让后续请求直接拿到"已拒绝"。验证授权流程时别反复重启。

顺序上有一点要注意：**四期可以提前到任何时候**，因为它不依赖二期的写机制。不过它本来也不是一道闸门——插件够不够得到不由我们决定（§5.3），四期做的是归因和警告，不是开门。

### 7.2 一到三期验证情况（2026-11-09，iPhone 14 Pro Max / iOS 26.6.2）

探针直连 addon（`process._linkedBinding`，`callerClaim` 报成 `probe`）——走的就是插件能走的那条路，不是引擎的特权通道。

**已验证（不需要人配合的部分）：**

| 项 | 结果 |
|---|---|
| 能力表 | 五项齐全，操作列表与 `CAPABILITIES` 一致：`device[info]`、`notify[schedule,cancel,pending]`、`speak[say,stop]`、`calendar[list,calendars,create,update,delete]`、`reminders[list,create,complete,delete]` |
| `device.info` | **第一次调用就拿到电量 70%**，零期修的那个「第一次总是 unknown」没有回潮 |

| 未知能力 | `healthkit.read` → `unknown capability 'healthkit'` |
| 引擎测试 | 125 项，0 失败 |

- 日历和提醒的**系统授权弹窗**，以及授权后的读取。
- **写**的三条路：`create` 弹系统事件编辑器、`update` / `delete` 弹原生确认框、提醒的三个写操作。
- **使用记录页**的实际显示（调用方、摘要、清空）。
- **示例插件**装上之后，使用记录里调用方显示成插件名。
- 日历「仅添加」那一档的提示（`simctl privacy` 和真机都不好构造这个状态）。

**为什么不顺手把授权弹窗也跑了：** §7.1 记过一条——授权弹窗没人应答时若 App 被重启，后续请求会直接拿到「已拒绝」，而 iOS 一个 App 一生只弹一次。在没人看着的情况下触发它，有把权限永久弄成拒绝的风险，只能回系统设置救。所以这一段留给人跑。

**上面那条「写操作必须人在手机前面」后来推翻了一半：** 模拟器可以自己点。真机上注入不了点击（Wi-Fi 配对的 iOS 26 设备 `libimobiledevice` 看不见），但模拟器的全部界面都能驱动，而要验的那几条链路——系统授权框、事件编辑器、确认框——在模拟器上是同一套代码。于是写操作和授权流程改在模拟器上验，见 §7.3。**它一跑就抓出三个真机探针抓不到的 bug。**

**那条「没验证到但值得先记下的风险」应验了**：`create` 走 `EKEventEditViewController` 时不要求权限这个假设是**错的**，而且代价不是一个报错，是一次挂死。详见 §7.3 和 §4.3.2。

### 7.3 授权与写操作验证（2026-11-10，iPhone 17 Pro Max 模拟器 / iOS 26.4）

真机只能验引擎侧；要点的那些界面改在模拟器上验，因为模拟器能驱动全部 UI，而这几条链路两边是同一套代码。**这一轮抓出三个 bug，全部在"可信"那条路上**——真机探针一个都碰不到，因为它们都要有人真的把界面点完。

**抓到的三个：**

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `calendar.create` **永远不返回** | `EKEventEditViewController` 是跨进程扩展，没权限时起来即自毁（`OOP EventEditView: interruptionHandler`），代理回调永远不来。而 `create` 当时**跳过了授权检查**，理由是"Apple 的界面不需要权限" | 先过 `with_add_access`（"仅添加"那一档就够）；并给桥上每个等待配看门狗（§4.3.2） |
| 2 | 新建提醒时，框问**「修改这个日程？」** | `confirmChange` 只知道 `destructive`，不知道是哪项能力、哪个操作 | 协议改成带 `capability` + `op`，标题在 Swift 侧按对照表拼——和使用记录同一套（那边本来就分得清） |
| 3 | 使用记录里出现一条**用户已经点了取消**的「日历 · 修改日程」 | 分发器的条件是「没出错就记」，而取消返回的是 `{saved:false}`，不算错 | 条件改成「有摘要才记」。摘要只有写成功才给，所以这条规则是结构性的，不靠以后每个新能力都记得 |

第 3 个最值得记：审计页是用户事后唯一的凭据，**记错一条比少记一条更糟**——它会让一次被拒绝的写看起来发生过。

**验过的（我自己点完全程）：**

| 项 | 结果 |
|---|---|
| 未授权时的五项调用 | 全部直接拒绝，没有任何弹框：`calendar.list` 20ms、`calendar.create` 134ms、`reminders.list` 15ms、`notify.schedule` 1.9s；`device.info` 正常返回（它不需要授权） |
| 授权入口 | 侧边栏「本机能力 · 授权」→ 点「开启」→ 系统框出现在能力页之上，用途描述（含"会随对话发送给你选择的模型服务商"那句）完整显示 |
| 授权后状态 | 该项立刻变「已开启」，图标转实心，按钮消失 |
| `calendar.create` | Apple 事件编辑器，字段全部预填；点 ✓ → `{saved:true, id}` |
| `calendar.update` **取消** | `{saved:false, action:'cancelled'}`，而且标题**真的没变** |
| `calendar.update` 确认 | `{saved:true}` |
| `calendar.delete` | 确认框是红色破坏性样式；点删除 → `{deleted:true}` |
| `reminders` 三个写 | create / complete / delete 各弹一次确认，全部 `saved`/`deleted` 为真 |
| 使用记录 | 六条，按「能力 · 操作」分别显示中文名，带摘要和调用方 `probe`；被取消的那次**修完之后**不再出现 |

**还是没验到的：**

- **真机上的这一整套**。模拟器和真机在这几个框上是同一套代码，但 EventKit 的跨进程扩展行为在真机上未必一样——bug 1 恰恰就是跨进程扩展的行为问题。
- **示例插件**装上之后，使用记录里调用方显示成插件名（探针报的是 `probe`，已经证明这一栏确实来自调用方自报的字符串）。
- 日历**「仅添加」**那一档：`simctl privacy` 给不出这个状态，只能在真机系统设置里手动选。

### 7.4 第二批能力的实地验证（2026-11-10，模拟器）

`open` / `nlp` / `maps` / `vision` / `clipboard` / `location` 六项。跑一遍又抓出三个只有在真设备上才看得见的问题，全部是「我的设计假设错了」，不是实现写错了。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `nlp.similar` 把余弦值当相关度交出去 | 实测：完全相同的句子 1.000，正确的最佳匹配只有 **0.102**，无关的 -0.323。**顺序有意义，数值没有** | 渲染只给名次，数值留在 JSON 里改名 `cosine`；工具说明直说「这是排序不是打分，低分不代表不相关」 |
| 2 | `"dog"` 被判成丹麦语 | 三个字母判不出语种，而短查询是常态 | 拿查询 + 候选项一起判，候选里文字足够多 |
| 3 | `maps` 给出自信的错答案 | `MKLocalSearch` 按设备区域排商户：从中国区查「San Francisco」得到「San Francisco Bakery」，两端都错，ETA 2989 公里 | 改用 `CLGeocoder` 解析地名——但这只是第一步，见下 |

**第 3 个修到一半又翻车，值得单独记：**

改成 `CLGeocoder` 之后，「San Francisco」被解析成**云南普洱磨黑上安宁**，两端解析到同一个地方，ETA 变成「1 米 1 秒」。原因是**设备在中国区时 Apple 的地理编码走国内服务商，它不知道国外地名，但它不报错**——它给你一个别的地方。

所以根子不在用哪个 API，在于**不该默默拿 `.firstObject` 当答案**。

当时的修法是加一条「解析结果得和问题对得上」的检查（`DshGeocodePlausible`），对不上就拒绝并说清它给了什么。**这个修法是有效的** —— 复验时「San Francisco」被正确拒绝、「北京市→天津市」正常出 137 公里。

**但它随后被整个删掉了，因为形状不对。** 它是我们自己发明的字符串相似度规则，而且上线前就已经打过一个补丁（中文查询对英文结果字面无交集，要加 `preferredLocale` 才压住），后面还有缩写、音译、别名等着。能跑，但要养一辈子。最终做法见 §4.5：**不挑**——`eta`/`route` 只收坐标，`geocode` 返回全部候选，让模型自己一眼看出云南不是 San Francisco。

`preferredLocale` 留着，但理由变了：它不再是为了让比较成立，而是为了让中文用户拿到中文地名。选调用的参数是我们该做的，从答案里挑不是。

一条顺带的取舍：`CLGeocoder` 在 iOS 26 已废弃（Apple 指向 `MKGeocodingRequest`），但本项目部署目标是 **iOS 17**，而 `MKGeocodingRequest` 是 26+ 才有。加可用性分支会让这段代码翻倍而今天行为毫无差别，所以继续用 `CLGeocoder`，等部署目标过 26 再换。

**`vision` 的四个操作里，模拟器只跑得了一个。** 实测：

| 操作 | 模拟器 |
|---|---|
| `text`（OCR） | ✅ 正常，认出了图里的两行字 |
| `barcodes` | ❌ `Could not create inference context` |
| `classify` | ❌ `Failed to create espresso context.`（espresso 是 CoreML 的推理引擎） |
| `faces` | ❌ `Could not create inference context` |

OCR 走的是另一条不依赖 CoreML 的管线，所以它能跑。其余三个要模型推理，模拟器没有对应的后端。**这是模拟器的限制，不是代码问题，但也意味着这三个操作到目前为止没有任何地方验证过** —— 下一次真机验证必须覆盖它们。

错误消息原样转给调用方，没有改写：Apple 说的是实话，而我们并不知道它为什么起不来（§4.5）。

**这批里两条值得留下的设计：**

- **`appGated`**：iOS 管不到、但确实碰用户数据的能力（剪贴板），由 App 自己把门，判断点仍在分发器里。界面上它是个 **Toggle 而不是单向的「开启」按钮**——单向按钮会让用户除了删 App 没有退路。
- **`vision` 的路径走 `dsh_root_real`**：它能读到的文件和插件用 `fs` 能读的完全一致。不扩大任何范围，只是省下把图片发给模型。实测 `/etc/passwd` 读不到。

| `files` | `pick {types: ["pdf"], multiple: true}` | 选择器里那个 `.txt` 被过滤掉了 |
| `files` | `types` 写成 `image`、`public.pdf`（都不是系统声明的类型） | 被拒绝并点名是哪个字符串 |
| `files` | 选择器开着时再调一次 | 「a file picker is already open and waiting for the user…」，没有弹第二个 |
| `files` | 点 ✕ 关掉；下滑关掉 | 两种都是 `{cancelled: true, files: []}`，都结算了，没有挂住（§4.3.2） |
| `music` | 能力页点开启 → 系统弹窗 → 允许 | 那一行变「已开启」，并出现写入策略的选择（默认「直接执行」） |
| `music` | `search` / `playlists` / `now` | 空结果；5 个系统智能歌单，曲目数都是 0；`{state: 'stopped', item: null}` |
| `music` | `search` 的参数检查 | 不认识的 `kind`、没给 `query` 各有一条错误 |
| `music` | `play {songs: ['12345']}` | 「no song in the library has id 12345, so nothing was played — not the other songs either…」 |
| `music` | 空队列上不带目标的 `play`、`pause`、`next` | 都返回「命令已发出」，`item` / `from` 是 `null`（见下） |
| `weather` | `current` | 约 1.5 秒后：「Weather is not enabled for this build of the app yet…」，后面带框架原文 `WeatherDaemon.WDSJWTAuthenticatorServiceProxy.Errors error 0` |

**通讯录的匹配比预想的窄，这是这一轮最有用的发现。** 匹配规则完全是 Apple 的谓词，实测如下：

| 按什么查 | 能中 | 不中 |
|---|---|---|
| `phone` | 整个号码，写法可以不同（`8885555512`、`(555) 564-8583`） | 号码的一段；同一个号码前面加了 `+1`（`+1 888 555 5512`） |
| `email` | 整个地址，大小写不敏感 | 地址的一段 |
| `name` | 按词的前缀，公司名也算（`bell`、`Apple`、`Kate Bell`、`Creative`） | 词中间的一段（`ohn`） |

没有在原生侧把它放宽：自己拿号码去做包含匹配，就是在 Apple 的答案之外再造一套答案（§4.5）。做法是把这几条写进工具说明和内置 skill，让智能体知道拿一段号码查出来的空结果不等于「通讯录里没有这个人」。「加了国家码查不到」只在这台模拟器上看到过，真机上换一个地区设置可能不一样，没有验证。

**使用记录页对过一遍。** 按名字查显示「查询词 · 命中数」（`Kate Bell · 1`、`Anna · 0`），按电话、邮箱查只显示 `phone · 1` / `email · 1`，号码和地址本身没有出现；`get` 显示那张名片的名字。和 §3.2 写的一致。

**一处留着没改的取舍：音乐在空队列上的 `play`。** 返回的是 `played: true`、`item: null`，并且在使用记录里留下一条摘要为空的记录。这和「只记真发生的」不冲突 —— 命令确实发给了播放器，只是没有东西可播 —— 但那条空摘要的记录看起来像是出了错。要不要在 `item` 为空时不记，留给下一轮定。

**顺带修的一处：健康那一行的按钮跳错了地方。** 请求过健康授权之后，那一行的按钮原来是「去设置」，打开的是本 App 的系统设置页，而健康的逐项授权不在那里，在「健康」App 里（头像 → 隐私 → App）。现在按钮改成「打开健康」，直接开 `x-apple-health://`，那一行的说明和页脚也跟着改了。模拟器上点过，打开的是「健康」。

**界面文案三种语言都是全覆盖**（`scripts/strings-coverage.mjs`：`en` 和 `es` 都是 1594/1594）。英文界面在模拟器上逐行看过。

## 9. 参考实现：OpenMinis

[OpenMinis](https://github.com/OpenMinis/OpenMinis)（iOS + Android，**GPL-3.0**）是同类产品里走得最远的：on-device agent，iSH 沙盒里跑 Alpine Linux，把 Health / Calendar / Reminders / Photos / Location / HomeKit / Clipboard 等以工具形式交给 agent，**已经公开发布**。（**它不做通讯录**——2026-11-10 核对过注册表，没有 `apple-contacts`，也没有引用 `CNContactStore`。所以"同类产品都读通讯录了"这个依据不成立。）

> **许可证**：GPL-3.0，本项目是 MIT。按 `CONTRIBUTING.md` 的规矩，**只看思路，不拷代码**（文案也不抄）。下面是设计结论和可借鉴的教训，实现要自己写。

### 9.1 它印证了什么

| 我们的结论 | 它的做法 |
|---|---|
| 按能力授权，不按调用方（§2.2、§4.1） | 按 **offload 命令名**授权（`apple-healthkit`、`apple-calendar`…）。没有"本体 vs 插件"的概念 |
| 系统权限给了之后直接能用（§4.1） | 权限档位存 `UserDefaults`，读不到就是 `0`，而 `0 == bypass`——**默认就是不问直接用** |
| 原生侧是唯一执行点（§5.1 路线 A） | 所有 offload 由 native 分发，沙盒里的代码到不了框架 |
| 健康数据可以接 | HealthKit **读 + 写**都做了 |

### 9.2 它比我们的方案多出来的三个设计

**① 三档而不是开关。** `bypass` / `askOnce` / `notAllowed`，默认 `bypass`。
`askOnce` 是**按会话**授权：准过一次，这个会话内不再问，换会话重新问（没有会话上下文时落到一个 global 桶）。等待用户回答有 30 秒超时，**超时按拒绝**。

这比我们现在的"读无门、写每次确认"更细，而且 `askOnce` 同时适用于读和写。值得直接采纳：我们 §4.1 留的那个 policy 判断点，**形状就按这三档设计**，一期固定在 `bypass`，设置页以后再放出来——这样放出来时不用改任何调用方。

**② 按"是否碰个人数据"分类，只有碰的才给开关。**

- *privacy*（7 项，设置里可配）：healthkit / calendar / reminders / photos / location / homekit / clipboard
- *media*、*system*（13 项，永远 bypass，不进设置）：speak / speech / player / media / device / notification / alarm / open / maps / weather / nlp / vision

标准干净，直接可用：**不碰个人数据的能力不要给用户开关**，否则设置页会爆。顺带提醒我们 §3 漏了一批便宜又有用的东西——通知、闹钟、天气、地图、打开 URL、朗读，对"个人助理"价值不低，而且**不需要任何隐私权限**。

**③ 拒绝时给 agent 的是可操作的人话 + deep link。**
不是 `EPERM`，而是一句"用户关闭了 X，去设置 > 权限打开"外加一个 `minis://settings/permissions` 链接，agent 可以直接转述给用户点。我们有 `dsh://` scheme，照这个思路做。

### 9.3 最值得记的一条教训（它的 GH#242）

它的权限门曾被**一行路径**绕过：

- 门按 argv[0] 的**原始字符串**匹配命令名；
- 而 guest kernel 按 **basename** 分发（`strrchr`）；
- 于是 `/usr/local/bin/apple-healthkit` 在门那里匹配不到任何命令 → 返回 nil → 调用方把 nil 读成"这不是 offload 命令"→ **不检查直接放行**；kernel 照样按 basename 分发执行。
- 实机验证过：那个路径下是个 **0 字节占位文件**，却返回了真实的剪贴板 JSON——只可能是 native 分发干的。`Not Allowed` 也照样穿。

修复是让门用 kernel 的同一条规则。注释里那句话值得抄在墙上：

> 两套匹配规则 over 一个决定，一定会再次漂移。

**对我们的直接约束**，写进实现要求：

1. **能力判定用的键，必须就是分发用的那个键**，一张表，不许两张。
2. **检查点必须是唯一执行点**。addon 里碰 EventKit 的代码只有一处入口，不许为了方便再开一个"内部直调"的函数。
3. **要有测试钉住两个方向**：每种合法写法都被识别；不相关的名字不会因为"包含"注册名而继承它的权限。

它也诚实记下了没关掉的面：`sh -c '…'`、`env …`、脚本、子进程——这些情况命令名不出现在 argv[0]，门看不见。**我们的 addon 没有"命令名"这层间接**（收到的是结构化的能力 + 操作，不是一个要解析的 shell 字符串），所以这类拼写绕过从一开始就不存在——这是 addon 方案相对它那套 offload 命令的一个好处。
